API Optimizer

AI-powered API performance, intelligence and security platform · Architecture document

Version 2 · 15 November 2026 · Reflects the completed codebase: hardening, AI usage tracking, guardrails, assistant, RAG knowledge base, and the dashboard.

1. Purpose

API Optimizer sits in front of an HTTP API and makes it faster, safer and observable: Redis response caching cuts latency for repeated reads, token-bucket rate limiting protects the upstream, every request is measured and stored for analytics, and an LLM gateway with retries, fallback and a circuit breaker exposes chat completions. The AI layer adds an assistant that reasons over the measured data, a RAG pipeline over uploaded documentation, and basic guardrails around every model call.

2. System overview

Dashboard site/ · Next.js 14

Users, cache rules, one row per request (api_logs), hourly roll-ups. Schema managed by Alembic.

Redis

Response cache entries, LLM exact-match cache, token buckets, revoked-token denylist, cache hit/miss counters. Every use fails open.

LLM provider OpenAI-compatible

Chat Completions over HTTPS. OpenAI by default; any compatible server (Ollama locally) via OPENAI_BASE_URL.

Vector store implemented

ChromaDB on local disk for document chunks and embeddings (RAG).

3. Request pipeline

Starlette builds the middleware stack in reverse registration order, so the last middleware registered is the outermost. Every request passes through these layers in this order:

client ──► CORS ──► Metrics ──► CorrelationId ──► Auth ──► RateLimit ──► Cache ──► route handler CORS allowed browser origins (CORS_ORIGINS); exposes custom headers to JS Metrics wall-clock timing, JSON log line, X-Response-Time; APILog row + hourly roll-up written AFTER the response is sent CorrelationId X-Correlation-ID from the header or a new UUID; echoed back, in every log Auth Bearer JWT: type=access, signature, expiry, not revoked; sets request.state.user_id / role RateLimit token bucket per user (or IP); 429 + Retry-After when empty; fails open Cache GET with an enabled rule: serve from Redis (X-Cache-Hit) or store the 200 body after the handler ran (X-Cache-Stored)

Why this order: Auth runs before RateLimit so the limiter can key on the user, not just the IP. Cache is innermost so a cache hit still counts against the limit and still appears in analytics. Metrics is outermost so it measures everything, including rejected requests.

7. AI layer implemented

One new package, app/ai/, keeps the AI code separate from the request pipeline so an AI failure can never break caching, limiting or analytics.

provider

Thin wrapper over the existing ChatService; one LLM provider, swappable through OPENAI_BASE_URL.

assistant

Tool calling over a fixed set of analytics functions (summary, slow endpoints, cache stats, rate-limit events). No SQL from the model.

rag

ingest → extract (PDF, TXT, MD) → clean → chunk → embed → ChromaDB → retrieve top-k → build context → answer with sources, or say "not enough information".

guardrails

Length and type validation, prompt-injection heuristics, regex PII masking before the provider call, Pydantic output validation, grounding check against retrieved chunks.

user question ─► validate input ─► injection check ─► mask PII ─► metric tools OR vector retrieval ─► build context ─► LLM via the gateway (cache / retries / fallback / breaker) ─► validate output + cite sources ─► response ─► ai_request_logs (tokens, latency, estimated cost) + guardrail_events (what was flagged; never the raw prompt)

Retrieved document text is treated as untrusted data: it is placed in a clearly delimited context block, never as instructions, and uploaded files are scanned for instruction-like content at ingest time. Prompt-injection detection is heuristic and cannot guarantee complete protection; the audit log records what it caught.

8. Failure behaviour

Dependency downEffect
RedisRequests still succeed: no caching, no rate limiting, logout revocation not enforced, LLM cache bypassed. Health reports degraded.
DatabaseAuth, rules and analytics fail with controlled errors; analytics writes are logged and dropped, responses are unaffected.
LLM providerRetries with backoff → fallback model → circuit breaker opens for a cooldown → clean 503. Core API features unaffected.
Embedding model / vector store implementedUploads and searches return 503; assistant falls back to metric tools only.

9. Deployment and verification

  • Local: python scripts/migrate_db.py then uvicorn app.main:app; dashboard with npm run dev in site/; Redis via Docker.
  • Docker Compose: redis + backend; the image runs migrations before serving.
  • Render: render.yaml blueprint, scripts/migrate_db.py as pre-deploy command, secrets set in the dashboard. Dashboard on Vercel with NEXT_PUBLIC_API_URL.
  • CI: ruff over the repo, Alembic upgrade and downgrade on a scratch database, pytest against a real Redis, dashboard lint, type check and build.
  • Load test: k6 script compares cache off and on against the demo latency endpoint; results must be reported with VUs, duration and environment.
